# ICAN CRM — Service Operations
## الملخص التنفيذي لاتخاذ القرار

> نسخة مختصرة من المستند الكامل (`SERVICE-MASTER-SPEC.md`). الهدف: فهم الفكرة في 10 دقائق، ومعرفة المحسوم، والمطلوب قراره الآن.

---

## 1. الفكرة في سطرين

مديول **Service Operations** يدير رحلة العميل **بعد البيع**: التسليم، المتابعة، الدعم، التحصيل، والتجديد. يشتغل **مع السيلز** (العقد يحوّل العميل تلقائيًا) أو **لوحده** كباقة مستقلة، ويخدم **أي مجال بالإعدادات بدون كود جديد**.

```
Lead → Deal → Contract → Handoff → Service Delivery → Support → Follow-up → Renewal
```

---

## 2. المبدأ الحاكم

**اختلاف المجالات = إعدادات، مش كود.** ممنوع `if industry == tourism` في أي مكان.

```
Configuration  ← Templates, Item Types, Fields, Pipelines, SLA, Workflows, Portal
Engines        ← Cases, Records, Assets, Entitlements, SLA, Workflow, Scheduling
Shared Core    ← Customers, Conversations, Tasks, Calendar, Teams, Status, Assignment (الموجود)
```

**لا نبني CRM تاني جوه الـ CRM:** العملاء والمحادثات والمهام والتقويم والفرق تُستخدم كما هي.

## 3. القرارات المحسومة (لا تُعاد مناقشتها)

| # | القرار | السبب في سطر |
|---|---|---|
| 1 | **Modular Monolith** وليس Microservices | سرعة التنفيذ مع حدود قابلة للفصل لاحقًا |
| 2 | **Customer هو الهوية الوحيدة**، لا يوجد Account | منع تكرار بيانات العملاء |
| 3 | **Contact** = علاقة دائمة، **Participant** = مشارك في خدمة معينة (قد لا يكون Contact) | المستلم في الشحن لا يصبح عميل |
| 4 | **Event-Driven + Transactional Outbox** | لا فقد ولا تكرار للأحداث |
| 5 | **لا Event Sourcing** | مصدر الحقيقة هو قاعدة البيانات |
| 6 | **أعمدة ثابتة + JSONB** للحقول الديناميكية مع `schema_version` | مرونة بدون فقد الأداء |
| 7 | **Case** هو الكيان المركزي، والشكوى والطلب مجرد أنواع منه | محرك واحد لكل أنواع الطلبات |
| 8 | **Service Record** للخدمة المقدمة فقط (حجز، شحنة، تسجيل، اشتراك، مشروع) | منع الـ God Entity |
| 9 | **Asset، Work Order، Entitlement، Warranty** كيانات مستقلة | كل واحد له منطق مختلف |
| 10 | **Workflow Engine واحد مشترك** لكل ICAN | لا تكرار للأوتوميشن |
| 11 | **SLA Engine مستقل** عن الـ Workflow | دقة الحساب |
| 12 | **Snapshot لأي التزام** (عقد، SLA، جدول أقساط) | تعديل الإعدادات لا يغير التاريخ |
| 13 | **Billing Lite** بدون محاسبة (المحاسبة للـ ERP) | حدود واضحة مع الـ ERP |
| 14 | **AI يعطي إشارات، والقواعد تقرر** | لا قرارات حساسة آلية |
| 15 | **تعطيل Feature عليها بيانات = Read-only** | لا حذف أبدًا |
| 16 | **Messaging Policy** لكل رسالة خارجة | احترام قاعدة الـ 24 ساعة في WhatsApp |

## 4. خريطة الكيانات

```
Customer ─┬─ Contacts ── Relationships (guardian_of, manager_of...)
          │
          ├─ Contracts ── Payment Schedule (أقساط)
          │
          ├─ Service Records (حجز / شحنة / تسجيل / مشروع)
          │     ├─ Participants (مسافرين، مستلمين، طلاب)
          │     ├─ Components (طيران، فندق، انتقالات)
          │     ├─ Entries (حضور، درجات، محاولات توصيل)
          │     └─ Batch (مانيفست، رحلة جماعية، فصل)
          │
          ├─ Assets ── Warranty ── Entitlements (حقوق الخدمة)
          │
          └─ Cases ── Activities, SLA, Tasks, Work Orders
```

## 5. نماذج الخدمة (A–H)

كل مجال = نموذج أو تركيبة. النموذج **Preset** يفعّل قدرات افتراضية، مش منطق مكتوب في الكود.

| | النموذج | ينتج | أمثلة |
|---|---|---|---|
| **A** | بيع لمرة | Order + Cases | متاجر، ديجيتال |
| **B** | منتج + ما بعد البيع | Asset + Warranty | أجهزة، سيارات، عقارات |
| **C** | اشتراك | Subscription | SaaS، جيم، عقود صيانة |
| **D** | تسجيل | Enrollment + Entries | مدارس، سناتر |
| **E** | حجز | Booking + Components | سياحة، فنادق، عيادات |
| **F** | توصيل | Shipment + Batch | شحن |
| **G** | مشروع | Project + Milestones | Software House، مقاولات |
| **H** | خدمة عند الطلب | Case → Work Order | صيانة، تركيبات |

**أمثلة تركيبات:** وكيل أجهزة = A+B+C+H · مدرسة = D+C · شركة سوفتوير = C+G+H

---

## 6. الكتالوج: المنتج يتعرف بقدرات

المنتج مش هيكل ثابت. الـ Tenant يعرّف **Item Types** من **Capabilities** جاهزة:

| للمنتجات | للخدمات | مشتركة |
|---|---|---|
| وحدات، باركود، Serial، وحدة فريدة، إتاحة وحجز، Batch، صلاحية، Variants، تسليم رقمي | مواعيد، مراحل، سعة، مشاركين، زيارة ميدانية، مكونات، مستندات مطلوبة، تتبع | ضمان، تكرار (`every N unit`)، حقوق خدمة، أقساط |

**القاعدة:** لو المعلومة لها **سلوك** (تنبيه، تحقق، توليد) = Capability. لو **تُعرض فقط** = Custom Field.

**المنتج ممكن يكون عليه خدمات مرفقة** (مضمنة أو اختيارية): تكييف + تركيب مضمن + ضمان مضمن + عقد صيانة اختياري.

## 7. الأقساط (Billing Lite)

- **الخطة = قواعد** تُعرّف مرة في الإعدادات (مقدم، عدد، دورية، دفعة استلام، غرامات، تقريب، حدود).
- **تُربط** بنوع المنتج أو المشروع، **تُختار وتُعدّل** في الـ Deal (خارج الحدود = موافقة)، **وتتجمد** في العقد.
- **حجز مؤقت** للوحدة بمدة، ويرجع متاح تلقائيًا.
- **مصدر المدفوعات:** `crm` (يدوي) أو `erp` (تكامل) أو `gateway` (دفع أونلاين).
- **إعادة الجدولة والتنازل** = نسخة جديدة، القديم محفوظ.
- **COD** للشحن مع تسويات لعملاء الـ B2B.

**مثال:** وحدة 3,000,000، مقدم 10%، 32 قسط ربع سنوي، دفعة استلام 5%، وديعة صيانة 8% → الجدول يتولد تلقائيًا ومجموعه دقيق للقرش.

## 8. الربط مع السيلز

```
عقد موقع → Event → Handoff Processor
   كل بند في العقد → الكيان المناسب (Asset / Subscription / Booking / Work Order...)
   خطة السداد → جدول أقساط
   → Handoff (pending → accepted → onboarding → active)
   → رسالة ترحيب + دعوة البورتال + متابعات
```
- بند بدون إعداد → الـ Handoff يبقى `needs_review` بدل ما يفشل كله.
- تعديل العقد بعد التحويل → يُطبق الفرق فقط.

## 9. بوابة العميل

| نوع الوصول | مثال | الدخول |
|---|---|---|
| Self | عميل فرد | OTP واتساب/SMS |
| Guardian | ولي أمر يرى أبناءه | OTP |
| B2B Members | موظفي شركة عميلة بأدوار | Email/Password أو OTP |
| Guest | مستلم شحنة | رقم التتبع + OTP |

الصلاحية = **العلاقة + الدور + سياسة لكل كائن** (ولي الأمر يرى الدرجات ولا يعدّلها).

العميل يتابع: خدماته وآخر تحديث، تذاكره، أقساطه ويدفع، مستنداته ويرفع المطلوب، ويقيّم.

## 10. البنية التحتية المشتركة المطلوبة أولًا

Outbox + Queue (Retry، DLQ، Idempotency) · Scheduler مركزي · Audit Log · Permissions · Feature Flags والباقات · Custom Fields · تعميم Status و Assignment (بدون كسر السيلز) · Files · أرقام تسلسلية · تعدد اللغات · Messaging Policy.

**بدون الأساس ده، لا SLA ولا أوتوميشن ولا تكاملات هتشتغل صح.**

## 12. المطلوب قراره الآن

### قبل Phase 0 (عاجل)

| القرار | التوصية |
|---|---|
| الـ Stack | الحفاظ على الموجود |
| قاعدة البيانات | **PostgreSQL** (ضروري للـ JSONB والبحث العربي) |
| الـ Queue | Redis-based، أو RabbitMQ لو الحجم كبير |
| مزود WhatsApp | حسب الموجود في Conversations |
| الأحجام المتوقعة | 100–500 Tenant، أكبرهم ~5,000 Case/يوم (للتأكيد) |

### قبل Phase 3

| القرار | التوصية |
|---|---|
| مجالا الـ Pilot | **أجهزة/صيانة (B)** + **سياحة (E) أو تعليم (D)** |
| لحظة Deal Won | عند توقيع العقد (قابل للتغيير لكل Tenant) |
| هل يوجد عقود/فواتير حاليًا في السيلز؟ | يُراجع للترحيل |
| توقيع العقود | OTP داخلي أولًا |

### قبل Phase 4

| القرار | التوصية |
|---|---|
| الـ ERP الأول | Odoo |
| بوابات الدفع | Paymob + Fawry |
| تطبيق الفني/المندوب | PWA أولًا |
| تسعير الشحن | لاحقًا (لو الشحن مش Pilot) |

## 13. المخاطر الأساسية

| الخطر | التخفيف |
|---|---|
| **تضخم النطاق** وتأخر أول إصدار | الالتزام بـ MVP-1 بعد Phase 2 قبل أي توسع |
| **كسر السيلز** عند تعميم Status و Assignment | Tests للتوافق + Feature Flags للتحويل التدريجي |
| **التصميم يتفصّل على مجال واحد** | اختبار كل قرار على مجال ثاني قبل اعتماده |
| **أخطاء حسابية في الأقساط** | Tests حسابية شاملة + مجموع السطور = السعر دائمًا |
| **إيقاف رقم الواتساب** بسبب رسائل مخالفة | Messaging Policy إلزامية من Phase 0 |
| **تسريب بيانات بين الـ Tenants** | `tenant_id` على كل جدول + Tests آلية |
